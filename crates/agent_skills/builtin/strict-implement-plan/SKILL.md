# Implement Plan (/strict-implement-plan)

Выполняет готовый план из `.md`. **Не планируй заново** — цель реализовать документ. В этом режиме код редактировать можно и нужно.

## 1. Найди файл плана (строгий приоритет)

1. **Явная ссылка/@-упоминание** файла плана (`.md`) в этом же сообщении — беру её.
2. **Последний план, упомянутый в этом чате**: ссылка вида `file://.../plans/*.md` в недавней истории. «Последний документ» = самый свежий по ходу диалога.
3. **Самый свежий в хранилище**: посмотри содержимое `~/.agents/plans` — через `mcp:filesystem:list_directory` (если сервер доступен) или `ls -t ~/.agents/plans` (терминал) — свежие файлы сверху. Сначала ищи среди файлов текущего проекта (имя начинается с `<project>-`, где `<project>` — имя корневого каталога воркспейса, например `web-frontend-dev-2026-09-09-...`); если для текущего проекта планов нет — бери свежайший среди остальных.

Если ничего не нашлось или неоднозначно (несколько кандидатов) — задай **один** вопрос со списком кандидатов.

Подтверди выбор одной строкой: `▶ Implementing: <имя-файла>.md`

## 2. Прочитай и пойми план

- Файлы планов лежат в `~/.agents/plans/` (вне воркспейса). Читай их в порядке приоритета: `mcp:filesystem:read_text_file` (если сервер доступен) → `read_file` (если каталог добавлен как папка проекта) → `cat ~/.agents/plans/<имя>.md` (терминал).
- Прочитай план целиком, затем затронутые файлы кода — по ссылкам внутри плана (путь берётся из URL, фрагмент `#L{start}:{end}` указывает строки).
- Сверь номера строк в плане с реальным кодом: если строки «уехали» — работай по фактическому состоянию, а ссылки в плане актуализируй.

## 3. Реализация

- Иди по шагам **по порядку**; каждый шаг — законченное изменение, как написано в плане.
- Ссылки в плане — это навигация: открывай файлы реальным чтением, не полагайся на текст ссылки.
- Соблюдай рамки плана, включая секцию «Что не делаем»; за пределы плана не выходи без запроса.
- Соблюдай стандарты стека: загрузи скиллы `strict-*` для используемых языков/фреймворков (см. роутер в `AGENTS.md`).
- Упёрся в неоднозначность или противоречие → остановись и спроси пользователя, не додумывай молча.

### Отметка прогресса в файле плана

- Файл плана вне проекта — обновляй его через `mcp:filesystem:write_file`/`mcp:filesystem:edit_file` (если сервер доступен); иначе обычными инструментами (`edit_file`/`write_file`), если `~/.agents/plans` добавлен как папка проекта; иначе — перезапись целиком через терминал (`cat > ~/.agents/plans/<имя>.md <<'MD_EOF' ... MD_EOF`, кавычки у маркера обязательны).
- Отмечай выполненные шаги: `- [x]` + краткая пометка «что сделано». Делай это после каждого шага или компактного блока шагов, чтобы не тратить лишние операции, но файл всегда оставался актуальным.
- Если реальность разошлась с планом — дополняй шаг пометкой «изменено в ходе реализации: …», обновляй «уехавшие» ссылки на строки и сообщай о существенных отклонениях.

## 4. Проверка

- Прогони уместные проверки для затронутого кода: тесты / typecheck / lint / build — как принято в проекте (см. `package.json`, инструкции проекта).
- Ошибки от своих изменений исправь. Если план предполагал проверку — убедись, что она выполнена.

## 5. Итог

Одно финальное сообщение:

- что сделано по шагам (со ссылками на план);
- изменённые файлы — кликабельными ссылками Zed-формата с диапазонами: `[@путь/файл.ts (11:15)](file:///абс/путь/файл.ts#L11:15)`; одна строка — `#L{n}:{n}`;
- какие проверки прогнал и их результаты (или честно скажи, что не запускал и почему);
- отклонения от плана и причины.

В начале файла плана добавь строку статуса: `> ✅ Статус: выполнен <дата>`. Если план уже был выполнен ранее — скажи об этом и предложи следующие шаги, код не меняя.

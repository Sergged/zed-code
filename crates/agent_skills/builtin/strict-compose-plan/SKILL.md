# Plan Composition (/strict-compose-plan)

Режим планирования как в Devin Desktop / Google Antigravity: сначала проектируем, код не меняем.

КРИТИЧНО: пока активен этот режим и **не был вызван** скилл `strict-implement-plan`, менять файлы проекта запрещено — даже если пользователь просит внести код прямо в этом чате. Реализация начинается только после вызова `/strict-implement-plan`. Единственное, что здесь можно писать, — файл плана (см. ниже).

## 0. Вход в режим

- Подтверди режим одной строкой: `🧭 Compose Plan: только исследование и план — файлов проекта не касаюсь.`
- ЗАПРЕЩЕНО менять что-либо в проекте: редактировать, создавать, удалять, переименовывать, копировать или перемещать файлы и папки; запускать команды, которые пишут на диск (сборки, генераторы, `npm install` и т.п.); применять git-изменения (`checkout`, `reset`, `commit`, `stash`, `apply`).
- Терминал — только **readonly-команды**: чтение файлов (`cat`), поиск и навигация (`grep`, `find`, `ls`), readonly-git (`status`, `log`, `diff`, `show`, `blame`), `date` и подобные — ничего, что меняет состояние.
- Вопросы пользователю задавай через инструмент **`ask_user`** (варианты ответа + свободный ввод); он доступен, если включён в текущем профиле агента.
- Единственное исключение — сам файл плана: его можно создавать и обновлять в `~/.agents/plans` (или там, где явно попросил пользователь). Больше ничего не создаём и не меняем.

## 1. Разведка (research)

- Прочитай `AGENTS.md`/`CLAUDE.md` (если есть) и осмотри структуру проекта.
- Изучи затронутые файлы и связанный код: импорты, места использования, соседние модули (grep/чтение). Пользователь мог приложить ссылки на файлы/выделения — начни с них.
- Цель разведки — задавать пользователю предметные вопросы, а не «открытые».

## 2. Уточняющие вопросы

- Задай **2–5 коротких вопросов** (в `megaplan` — вдвое больше и глубже). Вопросы задавай через `ask_user` — по одному вопросу на вызов (пользователь может выбрать вариант или вписать свой ответ); так диалог похож на Devin. Если `ask_user` недоступен — компактным нумерованным списком в одном сообщении.
- Не задавай вопросов, ответы на которые очевидны из кода или уже данного ТЗ.
- Если пользователь написал «без вопросов», «сразу план» — пропусти этап вопросов.

## 3. Файл плана

Путь по умолчанию: `~/.agents/plans/<project>-YYYY-MM-DD-<slug>.md` — личное хранилище планов вне проектов (видно всем чатам); префикс проекта помогает отличать планы разных репозиториев.

- `<project>` — имя корневого каталога воркспейса, приведённое к kebab-case (lowercase, пробелы и спецсимволы — в дефисы), например `web-frontend-dev`. Дату получи через терминал: `date +%Y-%m-%d`. Slug — kebab-case от темы задачи.
  Пример имени: `web-frontend-dev-2026-09-09-ansible-multiselect-refactor.md`.
- Если каталога `~/.agents/plans` нет — создай: `mkdir -p ~/.agents/plans`.
- Если пользователь явно попросил хранить план в самом репозитории (например `<проект>/docs/plans/`) — положи туда и явно скажи об этом.
- Пиши план на языке пользователя (RU/EN).

### Как записывать файл (важно: каталог вне проекта)

`~/.agents/plans` находится за пределами воркспейса, поэтому обычные инструменты записи (`write_file`/`edit_file`) туда по умолчанию не работают. Инструменты для работы с файлами планов выбирай в таком порядке приоритета:

1. **MCP filesystem** — если доступны инструменты `mcp:filesystem:*` (контекст-сервер `filesystem` с корнем `~/.agents/plans`):
   - запись/правки: `mcp:filesystem:write_file`, `mcp:filesystem:edit_file`;
   - чтение/поиск: `mcp:filesystem:read_text_file`, `mcp:filesystem:list_directory`, `mcp:filesystem:search_files`, `mcp:filesystem:directory_tree`.
2. **Обычные инструменты Zed** — если пользователь добавил `~/.agents/plans` как дополнительную папку проекта (Add Folder to Project / второй корень воркспейса): `write_file`/`edit_file`/`read_file`.
3. **Терминал** — если ни MCP, ни папки-проекта нет:

- Запись нового файла heredoc'ом (кавычки у маркера обязательны — запрещают подстановки):

  ```sh
  cat > ~/.agents/plans/<project>-2026-09-09-<slug>.md <<'MD_EOF'
  <весь текст плана целиком>
  MD_EOF
  ```

- Обновление файла (правки плана) — перезапись целиком тем же способом: `cat > ... <<'MD_EOF' ... MD_EOF`.
- Чтение файла плана (в этом или другом чате) — `cat ~/.agents/plans/<имя>.md`.

### Ссылки на файлы — только Zed-формат (критично)

Каждое упоминание файла в плане — кликабельная ссылка (cmd+click откроет файл/строки):

```
Весь файл:     [@путь/имя-файла.ts](file:///абсолютный/путь/имя-файла.ts)
Диапазон:      [@путь/имя-файла.ts (11:15)](file:///абсолютный/путь/имя-файла.ts#L11:15)
Одна строка:   [@путь/имя-файла.ts (11:11)](file:///абсолютный/путь/имя-файла.ts#L11:11)
```

Правила:

1. URL — **только абсолютный** (`file:///Users/...`). План лежит вне воркспейса, относительные ссылки не работают.
2. Формат фрагмента — `#L{start}:{end}` (диапазон) или `#L{n}:{n}` (одна строка).
3. Номера строк бери из реального чтения файла, **не выдумывай** их. Если хочешь сослаться на интерфейс/enum/функцию — перечитай файл и возьми точные строки.
4. В тексте ссылки указывай путь (в чате можно короткое имя файла, если однозначно).
5. Если после правок кода строки «уехали» — обновляй ссылки в плане.

Пример: `[@ansible.interface.ts (11:15)](file:///Users/sergey/dev/web-frontend-dev/src/app/modules/task/commons/components/ansible-params/ansible.interface.ts#L11:15)`

### Структура файла плана

```markdown
# <Заголовок: что делаем> (1–2 строки контекста)

## Цель и ожидаемый результат

## Контекст и факты

Что нашёл в коде — со ссылками на файлы (диапазоны строк).

## Шаги

- [ ] 1. Конкретное изменение: что, где (ссылка на файл/строки), как проверить.
- [ ] 2. ...

## Риски и открытые вопросы

## Критерии готовности

Как убедиться, что задача сделана (проверки, тесты, поведение).
```

Каждый шаг должен быть понятен **без этого чата** — файл плана будет читать реализация в новом чате.

## 4. Сводка (без вопроса о реализации)

После создания файла одним сообщением:

1. Краткая версия плана — 5–10 буллетов с сутью.
2. Кликабельная ссылка на файл плана: `[<project>-2026-09-09-...-slug.md](file:///Users/sergey/.agents/plans/<project>-2026-09-09-...-slug.md)` (cmd+click — открыть и прочитать).
3. Скажи, что план готов и что реализация запускается вызовом `/strict-implement-plan` (в этом или новом чате). **Не задавай вопрос «реализовать?» и не предлагай вариантов** — просто сообщи и дождись вызова `strict-implement-plan`.

## 5. Обработка ответов пользователя

- **Правки, вопросы, уточнения** → режим уточнения: отвечай и вноси изменения в **файл плана** (перезапись целиком, см. выше). После каждой существенной правки давай обновлённую краткую сводку. Код проекта не трогай.
- **Просьба реализовать / вызов `/strict-implement-plan`** → управление переходит скиллу `strict-implement-plan`; следуй его протоколу.
- **«нет / отмена / хватит»** → выйди из режима, план остаётся в файле — его можно реализовать позже через `/strict-implement-plan` (в т.ч. из нового чата по ссылке).
